A. LLM Models — Every Major Model, What It Is, When to Use It START HERE
What Is an LLM?

A Large Language Model (LLM) is a neural network trained on vast amounts of text to predict the next token. After training, it can generate coherent text, answer questions, write code, reason through problems, and call tools. You access it via an API — you send text in, you get text (or a structured object) back. You never "run" it locally in production (unless you use open-source models).

The key mental model: An LLM is a stateless function. Input = prompt. Output = completion. No memory between calls. Every conversation turn must re-send the full history. This is exactly like a stateless REST endpoint.

B. APIs & SDKs — OpenAI, Anthropic, Azure OpenAI, Spring AI — What Each Is TOOLING
The OpenAI API

The de-facto standard for LLM APIs. Everything else copies its shape. Key endpoints: /chat/completions (text generation), /embeddings (vector generation), /images/generations (image generation). Request = JSON with model, messages[], optional tools[]. Response = JSON with choices[].

When to use directly: When you need low-level control, are not in a Spring ecosystem, or are building something custom in Python/Node.js. The official Python SDK is openai. For Java, use the community openai-java SDK or Spring AI (preferred).

The Anthropic API (Claude)

Similar REST API shape but different field names — /messages endpoint, system is a top-level field (not a message role), tool definitions use slightly different schema. Not 100% OpenAI-compatible.

When to use directly: When you specifically need Claude's capabilities (longer context, strong instruction following) and aren't using an abstraction layer.

Azure OpenAI Service

Microsoft's hosted version of OpenAI models (GPT-4o, GPT-4o mini, embeddings). The API is nearly identical to OpenAI's, with two differences: you use a deployment name instead of a model name, and you authenticate with an Azure AD token or API key scoped to your Azure resource. SAP AI Core uses this under the hood for GPT models.

When to use: Enterprise/regulated environments where data must stay in Azure regions, or when your org has an existing Azure agreement. Required for SAP BTP AI Core integration.

Spring AI — The Java Abstraction Layer

Spring AI is a Spring Framework module (not a separate API provider). It wraps OpenAI, Azure OpenAI, Anthropic, Ollama, and others behind a unified Java interface. You switch providers by changing application.properties, not Java code.

How LangChain, LangGraph, and Spring AI Relate to Each Other

These are NOT competing — they operate at different levels:

  • LangChain = the toolbox. Gives you individual components (LLM wrappers, retrievers, memory, tools). Python-native.

D. Vector Databases — pgvector, Pinecone, Weaviate, MongoDB Atlas, HANA Cloud STORAGE LAYER
What Is a Vector Database?

A vector database stores embedding vectors alongside their source text (or metadata), and provides fast approximate nearest-neighbor (ANN) search — "find the K vectors most similar to this query vector." This is the retrieval engine in every RAG system.

Traditional databases (SQL, MongoDB) store data and let you filter/sort by value. A vector DB lets you search by meaning — "find documents semantically similar to this sentence" — which is impossible in SQL without storing and scanning every vector row by row (slow at scale).

Database analogy: A regular B-tree index is for exact or range lookups: WHERE age > 30. A vector index (HNSW or IVF) is for similarity lookups: WHERE meaning ≈ "cloud outage debugging". The index structure is fundamentally different — HNSW builds a hierarchical navigable graph of vectors for O(log n) approximate search.

E. Embedding Models — OpenAI, Cohere, Open-Source — What They Produce & When to Use Each RETRIEVAL QUALITY
What an Embedding Model Does

An embedding model takes text as input and outputs a fixed-length float vector. Unlike a chat model, it produces NO human-readable output — only numbers. Its quality is measured by how well its vectors capture semantic similarity, evaluated on the MTEB (Massive Text Embedding Benchmark).

The non-negotiable rule: Use the exact same embedding model at document ingest time and query time. Different models produce incompatible vector spaces — similarity scores become meaningless. Switching embedding models requires re-embedding all your documents.

1. How LLMs Actually Work at Inference Time — Tokens, Context Window, Temperature, Top-p FOUNDATION
The Core Idea: Next-Token Prediction

An LLM is, at its heart, a function: given a sequence of tokens, predict the probability distribution of the next token. That's it. Everything — reasoning, coding, conversation — emerges from doing this billions of times over a huge dataset until the probabilities are very good.

Think of it like a Kafka consumer that reads a stream of tokens and outputs a probability score for every word in its 100,000-word vocabulary. It then samples from that distribution, appends the chosen token to the stream, and repeats. The "intelligence" is the quality of the probability distribution, which is learned during training.

What Is a Token?

A token is not a word — it's a sub-word unit. The vocabulary is built using Byte-Pair Encoding (BPE): start with characters, repeatedly merge the most frequent adjacent pairs into new tokens until you have ~100K tokens. Results:

  • "the" → 1 token
  • "Kubernetes" → 3 tokens: Kub ern etes
  • "@SpringBootApplication" → 6+ tokens
  • 1 token ≈ 0.75 English words on average
Java analogy: Tokens are like the lexer output in a Java compiler — the raw source code gets split into meaningful units (keywords, identifiers, literals) before parsing. The LLM never "sees" raw characters; it sees token IDs.
Context Window — Why It's a Hard Constraint

The context window is the maximum number of tokens the model can "see" at once — both your input prompt AND the output it generates. GPT-4o: 128K tokens. Claude 3.5: 200K tokens.

Why does this limit exist? The attention mechanism in transformers is O(n²) in memory — every token must attend to every other token. Doubling the context quadruples the memory. This is a fundamental architectural constraint, not just an API limit.

Kafka analogy: The context window is like a Kafka consumer's in-memory buffer. You can only process what's in the buffer. If history exceeds the buffer, you must summarize (compact) old messages — exactly like Kafka log compaction. Anything outside the context window simply doesn't exist for the model.

Practical implication: In a chat application, if the conversation grows past the context limit, you must truncate old messages or summarize them. The model has no "memory" outside the context window — it's all stateless, exactly like an HTTP server.

Temperature — Controlling Randomness

After the model computes the probability distribution over all tokens, you sample from it. Temperature scales the distribution before sampling:

  • Temperature = 0: Always pick the highest-probability token. Deterministic, factual, repetitive. Use for: code generation, data extraction, classification.
  • Temperature = 0.7 (default): Balanced. Some randomness, still coherent. Use for: chat assistants, summaries.
  • Temperature = 1.5+: Very random. Creative but often incoherent. Use for: brainstorming, creative writing.
Math intuition: Softmax converts logits to probabilities. Temperature T divides every logit by T before softmax. Low T sharpens the distribution (winner takes more). High T flattens it (more uniform = more random). Setting T=0 is equivalent to argmax — always pick the top token.
Top-p (Nucleus Sampling) — A Smarter Sampling Strategy

Instead of sampling from ALL tokens in the vocabulary, top-p (also called nucleus sampling) only samples from the smallest set of tokens whose cumulative probability exceeds p.

Example with top_p = 0.9: rank all tokens by probability, sum them up until you hit 90%, and only sample from that "nucleus." If the model is confident (top few tokens dominate), the nucleus is tiny. If uncertain, the nucleus is large. This prevents sampling absurd low-probability tokens while preserving genuine uncertainty.

In practice: OpenAI recommends changing either temperature OR top_p, not both simultaneously. For factual/production tasks: temperature=0, top_p=1. For creative tasks: temperature=0.8, top_p=0.9.

2. Why RAG Exists — What Problem It Solves, RAG vs Fine-Tuning, When to Use Which CORE CONCEPT
The Core Problem: LLMs Have a Knowledge Cutoff and No Private Data

An LLM is trained on a static snapshot of the internet up to a cutoff date. It knows nothing about: your company's internal documents, your customer data, last week's incidents, or anything that changed after training. You also can't put 10 million documents into a prompt — the context window is too small.

There are two solutions: RAG (inject knowledge at query time) and fine-tuning (bake knowledge into the model weights). They solve fundamentally different problems.

How RAG Works — The Mechanism

RAG has two phases:

  1. Offline indexing: Take all your documents, split them into chunks, embed each chunk into a vector, store vector + text in a vector database. This runs once (and incrementally when documents change).
  2. Online retrieval + generation: When a user asks a question, embed the question, find the most similar document chunks (cosine similarity search), inject those chunks into the prompt as context, then call the LLM. The LLM answers using that injected context.
REST API analogy: RAG is like a REST API that does a DB lookup before responding. Your controller receives a request, calls the repository layer to fetch relevant data, and passes that data to the service that generates the response. The LLM is your service layer — it never hits a database directly; you fetch the data and hand it over.
Fine-Tuning — What It Actually Does

Fine-tuning continues training the model on your custom dataset, adjusting the model's weights. It's not "teaching facts" — it's teaching style, format, and behavior patterns.

Fine-tuning works well for: making a model always respond in JSON, always use a specific tone, follow a proprietary format, or apply domain-specific reasoning patterns. It does NOT work well for injecting facts — facts baked into weights can't be updated without retraining, and models notoriously "forget" or "confuse" factual fine-tuning with hallucinations.

3. Vector Embeddings — What Is a Vector, Why Cosine Similarity, What Makes a Good Embedding Model CORE CONCEPT
What Is a Vector Embedding?

An embedding model is a neural network that converts text into a fixed-length array of floating-point numbers — a vector. For example, OpenAI's text-embedding-3-small produces a vector of 1536 floats for any text input, whether it's 3 words or 3 paragraphs.

The key property: semantically similar texts produce numerically similar vectors. The model is trained so that "Java Spring Boot framework" and "enterprise Java web development" end up close together in 1536-dimensional space, while "Spring Boot" and "gardening tips" are far apart.

Java analogy: Think of an embedding as a hashCode() that measures semantic meaning instead of identity. A regular hashCode puts two different objects at completely different hash buckets regardless of how similar they are. An embedding puts similar objects in nearby buckets. It's like a hash function that preserves semantic distance.
Why Cosine Similarity (Not Euclidean Distance)?

You might ask: why not just use Euclidean distance (straight-line distance between two points in 1536D space)?

Because embedding vectors have a direction problem. The embedding model may produce vectors with different magnitudes for short vs. long texts (a 3-word phrase vs. a 3-paragraph document). Euclidean distance is sensitive to magnitude — long text embeddings can appear "far" from short text embeddings even when they're semantically identical.

Cosine similarity measures the angle between two vectors, ignoring their magnitudes. Two vectors pointing in the same direction have cosine similarity = 1.0 (identical meaning). Perpendicular vectors: 0 (unrelated). Opposite: -1 (antonyms).

cosine_similarity(A, B) = (A · B) / (|A| × |B|)

Example:
  "Spring Boot"  → [0.8, 0.1, 0.6, ...]  (1536 floats)
  "Java backend" → [0.7, 0.2, 0.5, ...]  (1536 floats)
  similarity = ~0.94  ← very close, correct

  "Spring Boot"  → [0.8, 0.1, 0.6, ...]
  "baking bread" → [0.1, 0.9, 0.1, ...]
  similarity = ~0.21  ← far apart, correct
Optimization note: OpenAI and most modern embedding models normalize their vectors to unit length (magnitude = 1). When vectors are unit-normalized, cosine similarity = dot product. Dot product is a single matrix multiplication — extremely fast on GPUs. This is why vector DBs can search billions of vectors in milliseconds.
What Makes a Good Embedding Model?

Not all embedding models are equal. The quality is measured on benchmarks like MTEB (Massive Text Embedding Benchmark). Key properties:

  1. Dimensionality: Higher dimensions = more expressive but more storage/compute. text-embedding-3-large = 3072D. text-embedding-3-small = 1536D. More is not always better for your use case.
  2. Domain alignment: A model trained on general web text may underperform on SAP technical documentation. Domain-specific embedding models (or fine-tuned ones) outperform general models on narrow tasks.
  3. Multilingual support: If your documents are in German, English, and Japanese, use a multilingual model like multilingual-e5-large.
  4. Critical rule: You MUST use the same embedding model at index time (when you embed documents) and query time (when you embed the user question). Using different models is like encoding a file as UTF-8 and trying to decode it as ASCII — the distances are meaningless.
Chunking — Why It Matters for Embedding Quality

You can't embed an entire 200-page PDF as one vector — you'd lose all granularity, and a single question about page 5 would retrieve the whole document. You split documents into chunks first, then embed each chunk separately.

  • Fixed-size chunking: Every chunk = 512 tokens, 50-token overlap. Simple, predictable, loses semantic structure.
  • Recursive character splitting: Try to split on paragraph boundaries first, then sentences, then words. Preserves natural semantic units.
  • Semantic chunking: Embed sentences, find points where similarity drops (topic boundary), split there. Best quality, most expensive.
Rule of thumb: Chunk size should match the granularity of your expected questions. If users ask about specific API parameters, small chunks (128 tokens) work better. If they ask about architectural decisions, larger chunks (512–1024 tokens) are better.

4. LangChain Architecture — Chains, Agents, Tools, Memory — How They Connect FRAMEWORK
What LangChain Actually Is

LangChain is a Python/JavaScript framework that provides reusable building blocks for LLM applications. Think of it as Spring Framework for AI — it doesn't do the AI itself, it gives you abstractions so you don't have to wire everything from scratch.

The core insight: an LLM application is always a composition of the same building blocks — prompt templates, model calls, output parsers, retrieval, memory, tools. LangChain standardizes the interfaces between them.

Spring analogy: LangChain is to LLM apps what Spring MVC is to web apps. Spring MVC gives you DispatcherServlet, Controllers, Services, Repositories — standardized layers. LangChain gives you PromptTemplate, LLM, OutputParser, Retriever, Memory — standardized LLM pipeline layers.
Core Building Block 1: PromptTemplate

A PromptTemplate is a string template with variables. At runtime you fill in the variables and get a complete prompt. It's exactly like a Java String.format() or Thymeleaf template — separation of structure from data.

template = """
You are a helpful SAP assistant.
Context: {context}
Question: {question}
Answer only from the context provided.
"""
# Fill in variables → final prompt string sent to LLM
Core Building Block 2: LCEL Chains (LangChain Expression Language)

LCEL is the modern LangChain syntax for composing components. Every component is a Runnable — it has an invoke() method. You compose Runnables with the pipe operator:

chain = prompt_template | llm | output_parser
result = chain.invoke({"context": docs, "question": user_query})

The output of each step is the input to the next. This is function composition — exactly like Java's Function.andThen():

Function<PromptValue, AIMessage> step2 = llm::invoke;
Function<AIMessage, String> step3 = outputParser::invoke;
Function<Map, String> chain = step1.andThen(step2).andThen(step3);
Core Building Block 3: Retriever

A Retriever wraps a VectorStore and exposes a get_relevant_documents(query) method. You embed the query, search the vector DB, return the top-K chunks as Document objects. The Retriever is the bridge between your knowledge base and the chain.

Core Building Block 4: Memory

By default, every LLM call is stateless — it doesn't remember previous turns. Memory in LangChain is a component that manages conversation history by appending it to the prompt. Types:

  • ConversationBufferMemory — full history, grows unboundedly, hits context limit fast
  • ConversationSummaryMemory — summarizes old turns using another LLM call, stays compact
  • ConversationBufferWindowMemory — keep only last K turns
Kafka analogy: LangChain Memory is like a Kafka consumer that maintains offset tracking. The "offset" is how much history to retain. ConversationBufferMemory is like never committing offsets (full replay from start). ConversationSummaryMemory is like log compaction — summarize old messages and discard originals.
Core Building Block 5: Agents and Tools

A Tool is any Python function annotated with a name and description. An Agent is an LLM loop that decides which tool to call next, calls it, reads the result, and repeats until done. The LLM chooses tools purely based on their text descriptions — this is why description quality matters more than implementation quality.

5. LangGraph — Why Graphs Over Chains? Nodes, Edges, State, Cycles — Real Use Case ADVANCED
The Problem With Chains for Agents

A LangChain chain is a directed acyclic graph (DAG) — it flows in one direction, no loops, no branching. This works great for simple pipelines: prompt → LLM → parser → done.

But real agentic workflows are NOT DAGs. They need:

  • Cycles: "Generate answer → validate → if invalid, regenerate" (a loop)
  • Conditional branching: "If classification is P1 → alert immediately; else → create ticket"
  • Human-in-the-loop: Pause at a node, wait for human approval, resume
  • Parallel execution: Run two tools concurrently, merge results

LangChain's AgentExecutor implements a hard-coded while-loop: think → act → observe → repeat. You can't add conditional branches or pauses without hacking the internals. LangGraph makes the control flow explicit and configurable.

Microservices analogy: LangChain chains are like a synchronous REST call chain — service A calls B calls C, linear, no branches. LangGraph is like a workflow engine (think Camunda or AWS Step Functions) — you define states, transitions, conditions, and the engine manages execution. You've traded simplicity for control.
LangGraph Core Concepts

State: A TypedDict (Python) or Pydantic model that represents everything the graph knows at any point — the conversation history, retrieved documents, current results, error counts, etc. Every node reads from and writes to this shared state. This is the single source of truth for the entire agent run.

Nodes: Python functions that take the current state and return an updated state. Each node is one logical step: "call the LLM," "run the retriever," "validate the output." Nodes are pure functions — they don't call other nodes directly.

Edges: Define which node runs after which. Three types:

  • Normal edge: A → B always, unconditionally
  • Conditional edge: A → B or C based on a function that inspects state
  • Cycle edge: B → A to loop back — this is what makes agents possible
Real Use Case: Self-Correcting Code Generator
State = { messages, code, error, attempt_count }

Nodes:
  generate_code(state)  → call LLM to write code
  execute_code(state)   → run code in sandbox
  check_result(state)   → did it pass tests?

Edges:
  generate_code  → execute_code         (always)
  execute_code   → check_result         (always)
  check_result   → END                  (if tests pass)
  check_result   → generate_code        (if tests fail AND attempt < 3)
  check_result   → human_review         (if attempt >= 3)

This workflow is impossible to express cleanly in a LangChain chain. In LangGraph, it's 15 lines of configuration.

Checkpointing — Why It Matters for Production

LangGraph supports checkpointing: saving the full state to a persistent store (PostgreSQL, Redis) at every node. This enables:

  • Resumability: If the agent crashes mid-run, restart from last checkpoint
  • Human review: Pause at a "needs approval" node, save state, let a human review, resume — even hours later
  • Debugging: Replay any run step-by-step by loading saved states
SAP BTP angle: In a production BTP application, LangGraph + PostgreSQL checkpointing means your AI workflow can survive CF app restarts. Long-running incident triage agents that need human approval can be safely paused and resumed.

6. AI Agents — ReAct Loop (Reason + Act), Tool Calling, When Agents Fail and Why CORE CONCEPT
What Makes Something an "Agent"

An LLM call is not an agent. An agent is an LLM in a loop that can:

  1. Decide what to do next (not just generate text)
  2. Execute an action (call a tool, run code, query a DB)
  3. Observe the result and update its plan
  4. Repeat until the goal is reached

The key word is loop. Without the loop, it's just a pipeline. With the loop and tool-calling ability, it becomes an agent.

The ReAct Pattern — Reasoning + Acting Interleaved

ReAct (from the 2022 paper "ReAct: Synergizing Reasoning and Acting in Language Models") is a prompting strategy where the LLM is instructed to alternate between writing its reasoning (Thought) and specifying an action (Act), then receiving the result (Observation), and repeating.

User: What is the current status of incident INC-4521?

Thought: I need to look up the incident status. I should use the get_incident_status tool.
Action: get_incident_status(incident_id="INC-4521")
Observation: {"status": "P1 - Active", "assigned_to": "team-sre", "opened_at": "2026-08-07T14:32Z"}

Thought: I have the status. The incident is P1 and active. I can now answer.
Final Answer: Incident INC-4521 is currently a P1 priority, actively being worked on by team-sre, opened at 14:32 UTC today.

The Thought step is crucial — it forces the model to plan before acting, which significantly improves accuracy on multi-step tasks compared to acting without reasoning.

Debuggability: The Thought/Action/Observation trace is extremely valuable for debugging. You can see exactly why the agent made each decision. This is like having a stack trace for LLM reasoning — something raw LLM calls don't give you.
When Agents Fail — And Why

Agents fail in predictable ways. Understanding these failure modes lets you design defensively:

1. Infinite loops: The agent keeps calling the same tool repeatedly because it can't determine it has enough information to stop. Fix: set max_iterations (e.g., 10) and a hard timeout. Always.
2. Wrong tool selection: The LLM picks the wrong tool because the description is ambiguous. Two tools with similar descriptions cause constant confusion. Fix: write tool descriptions as precise contracts, not marketing copy.
3. Hallucinated tool arguments: The LLM calls a real tool with made-up parameter values. Fix: validate tool inputs against a JSON schema before execution, return a clear error message the agent can react to.
4. Context window overflow: Long ReAct traces fill the context window. The agent "forgets" earlier observations and makes contradictory decisions. Fix: summarize old observations, use LangGraph checkpointing to persist state outside the context.
5. Cascading errors: Tool A returns an error → agent misinterprets it → calls Tool B with wrong input → chain of failures. Fix: each tool must return structured error objects with clear error codes, not generic exception messages.

7. Multi-Agent Systems — Orchestrator vs Worker Pattern, How Agents Communicate ADVANCED
Why Multiple Agents?

A single agent handling a complex task accumulates a long ReAct trace, filling the context window and degrading performance. More importantly, a generalist agent is worse at specialized tasks than a focused specialist.

Multi-agent systems apply the microservices principle to AI agents: decompose a large problem into focused sub-problems, each handled by a specialist agent that has only the tools and context it needs.

Microservices analogy: A monolithic agent is like a monolith service — it can do everything, but it's hard to scale, debug, and improve. Multiple specialist agents are like microservices — each owns its domain, communicates via defined interfaces, and can be independently improved or scaled.
Orchestrator-Worker Pattern

The most common multi-agent architecture:

  • Orchestrator agent: Receives the high-level goal, breaks it into subtasks, delegates each subtask to the appropriate worker agent, monitors results, and synthesizes the final answer. The orchestrator is typically a more capable (expensive) model.
  • Worker agents: Each is focused on one capability. They receive a specific task, execute it with their tools, and return a result. Workers can be cheaper, faster models.
User: "Analyze this cloud incident log, find the root cause, and draft a postmortem."

Orchestrator breaks it down:
  → Task 1 to LogAnalysisAgent: "Extract error patterns from this log"
  → Task 2 to KnowledgeAgent: "Find similar past incidents in the runbook DB"
  → Task 3 to WriterAgent: "Draft postmortem from these findings"
  ← Orchestrator merges results → Final postmortem
How Agents Communicate

Agent-to-agent communication is just structured messages. In practice, two patterns:

  1. Direct function calls (in-process): The orchestrator calls worker agents as Python functions. Simple, fast, synchronous. Works for small systems. LangGraph implements this natively — worker agents are just nodes in the parent graph.
  2. Message queues (distributed): Each agent is a separate service. The orchestrator publishes tasks to a Kafka topic (or Redis queue); workers consume, process, and publish results back. This is exactly how you'd design microservices — and it handles scale, retries, and fault isolation.
Kafka parallel: Multi-agent via Kafka is structurally identical to event-driven microservices. Orchestrator = event producer. Worker agents = Kafka consumers with their own consumer groups. Results = events on a reply topic. The agent framework is just a thin wrapper around patterns you already know.
Critical Engineering Concerns
  • Shared state: Workers need to see each other's intermediate results. Use a shared state store (Redis, PostgreSQL) — don't try to pass everything through message payloads.
  • Stopping conditions: Define explicit termination criteria. Without them, agents can create loops where Worker A's output triggers Worker B which triggers Worker A forever.
  • Result aggregation: When two workers produce conflicting outputs (e.g., one says root cause is Service A, another says Service B), the orchestrator must have a strategy — majority vote, confidence scoring, or escalation to human.
  • Cost control: Multi-agent = multiple LLM calls. A chain of 5 agents each making 3 tool calls = 15+ API calls per user request. Model routing (cheap model for workers, expensive for orchestrator) is not optional.

8. Function Calling in OpenAI/Claude API — How It Works Mechanically, JSON Schema, Parallel Calls FRAMEWORK
What Function Calling Actually Is

Function calling is often misunderstood. The LLM does NOT execute your code. It produces a structured JSON object describing which function to call and with what arguments. You execute the function. You return the result. The LLM just decides when and how to ask.

The mechanism: you include a list of function schemas in your API request. The LLM, when it decides a function would help, returns a special tool_call object instead of (or alongside) text. Your application reads that object, runs the function, and makes a second API call with the function result appended to the conversation.

The Full Mechanical Flow
// Step 1: You send a request with tool definitions
{
  "model": "gpt-4o",
  "messages": [{"role": "user", "content": "What's the status of INC-4521?"}],
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "get_incident_status",
        "description": "Retrieves current status, severity, and assignee for a cloud incident by ID.",
        "parameters": {
          "type": "object",
          "properties": {
            "incident_id": { "type": "string", "description": "The incident ID, e.g. INC-4521" }
          },
          "required": ["incident_id"]
        }
      }
    }
  ]
}

// Step 2: LLM returns a tool_call (NOT the final answer)
{
  "choices": [{
    "message": {
      "role": "assistant",
      "tool_calls": [{
        "id": "call_abc123",
        "type": "function",
        "function": { "name": "get_incident_status", "arguments": "{\"incident_id\": \"INC-4521\"}" }
      }]
    },
    "finish_reason": "tool_calls"   // ← NOT "stop", means tool call pending
  }]
}

// Step 3: You execute get_incident_status("INC-4521") → get result
// Step 4: You append the result as a "tool" role message
{
  "role": "tool",
  "tool_call_id": "call_abc123",
  "content": "{\"status\": \"P1 Active\", \"team\": \"sre-cloud\"}"
}

// Step 5: Send updated conversation → LLM generates final answer
REST API analogy: This is exactly like an API gateway with a backend call. The LLM is the gateway — it receives the request, determines it needs backend data (tool_call), you fetch from the backend (execute function), you return the data (tool message), and the gateway generates the final response. The LLM is never calling your code directly, just like a gateway never calls the DB directly — it delegates.
Parallel Function Calls

Modern models (GPT-4o, Claude 3.5) support parallel tool calls — the LLM can request multiple tool calls in a single response when it can determine they're independent:

// LLM returns TWO tool calls in one response:
"tool_calls": [
  { "id": "call_1", "function": { "name": "get_incident_status", "arguments": "{\"id\":\"INC-4521\"}" }},
  { "id": "call_2", "function": { "name": "get_service_health",  "arguments": "{\"service\":\"auth-svc\"}" }}
]

// You execute BOTH in parallel (e.g., two async HTTP calls)
// Return both results → LLM synthesizes a combined answer

This dramatically reduces latency when the agent needs data from multiple sources. You should execute parallel tool calls concurrently — sequential execution throws away the performance benefit.

The Critical Importance of Descriptions

The LLM decides which function to call, and with what arguments, based entirely on the text descriptions in the schema. This is unlike a regular API where the caller knows exactly what to call. Here, the LLM reads your function name and description and infers intent.

Bad description: "name": "lookup", "description": "Looks up data" — The LLM has no idea when to use this. It will use it randomly or never.

Good description: "name": "get_incident_status", "description": "Retrieves the current status, severity level (P1-P4), assigned team, and opened timestamp for a cloud operations incident by its ID. Use when the user asks about an active or recent incident."

9. Guardrails and Hallucination — Why LLMs Hallucinate, How to Detect and Reduce It PRODUCTION CRITICAL
Why LLMs Hallucinate — The Root Cause

Hallucination is not a bug that will be fixed in the next model version. It's a fundamental property of how LLMs work: they are trained to predict the most probable next token, not to verify truth. Probability and truth are not the same thing.

During training, the model learned that plausible-sounding statements follow plausible-sounding statements. It has no mechanism to distinguish "I know this" from "this sounds like it could be true." When asked about something it doesn't know, it doesn't say "I don't know" — it says the most statistically likely thing, which may be false.

Code analogy: Imagine a code auto-complete trained on millions of Stack Overflow posts. It will confidently suggest API calls that don't exist because it learned that someObject.doSomething() often appears in that context — even if doSomething() was never defined. That's hallucination: the model produces statistically plausible output that's factually wrong.

Three specific triggers for hallucination:

  1. Knowledge gaps: The model is asked about events after its training cutoff, proprietary data it was never trained on, or obscure facts underrepresented in training data.
  2. Leading questions: "Confirm that service X caused the outage" nudges the model toward agreement even if it's not true. The model is optimized to be helpful, and agreeing is often the most "helpful"-seeming response.
  3. Long context: The model loses track of details in very long prompts. It may contradict information stated earlier or misremember constraints.
Detection Strategies
  • Self-consistency: Ask the model the same question 3–5 times with temperature > 0. If the answers vary significantly, the model is uncertain. High variance = high hallucination risk. Flag for human review.
  • Citation verification: If you're using RAG, require the model to cite which document chunk it used. Post-process: verify the cited chunk actually exists and actually says what the model claims. Spring AI's QuestionAnswerAdvisor can inject source metadata automatically.
  • Entity cross-validation: Extract named entities from the output (service names, API names, version numbers) and check them against a known registry. If the model mentions "auth-service-v3" and your service registry has no such service, flag it.
Reduction Strategies — Defense in Depth
Layer 1 — Prevent:
Grounding prompt: "Answer ONLY using the provided context. If the answer is not in the context, respond exactly: 'I don't have information about this.'" This single instruction eliminates most hallucinations for RAG systems.
Layer 2 — Reduce:
Temperature = 0 for factual tasks. Deterministic sampling eliminates the randomness that produces creative but wrong outputs.
Layer 3 — Detect:
Output parser with retry: if the output doesn't match expected schema or contains flagged patterns (specific service names, version numbers not in context), retry with a stricter prompt up to N times.
Layer 4 — Catch:
Guardrails advisor as post-processing: a second LLM call (cheap model) or a classifier that checks the output for hallucination signals before returning to the user. In Spring AI, this is an Advisor in the chain.
What does NOT work: Asking the model "are you sure about this?" — the model will just confidently affirm the hallucination. Verbal confirmation prompts have near-zero effect on factual accuracy. Use structural/architectural controls, not conversational reassurance.

How Pricing Works

LLM APIs charge separately for input tokens (everything in your prompt) and output tokens (everything the model generates). Output tokens are typically 3–5× more expensive than input tokens because generation is computationally heavier than reading.

Claude Sonnet: Input: $3.00 / 1M tokens  Output: $15.00 / 1M tokens

You should count tokens before sending a request for two reasons: (1) avoid hitting context window limits with a cryptic 400 error, and (2) proactively trim context before costs spiral.

  • Java: jtokkit library — same BPE algorithm, Java port

Prompt Compression — Where to Cut Tokens
  1. System prompt trimming: Your system prompt runs on every single API call. A bloated 500-token system prompt costs 500 × (calls per day) × (price). Remove filler phrases, use abbreviations for repeated terms, be terse. Write system prompts like you're paying per character — you are.
  2. Chat history summarization: Instead of appending all previous turns (O(n) growth), summarize older turns into a compact paragraph when they exceed a threshold. Use a cheap model (Haiku, GPT-4o mini) for the summarization call itself.
  3. RAG chunk tuning: Every retrieved document chunk costs tokens. Retrieving 5 chunks of 512 tokens = 2560 prompt tokens per query. Optimize: smaller chunks for precise questions, limit to top-3 not top-10, filter by metadata before vector search to retrieve fewer but more relevant chunks.
  4. max_tokens cap: Always set max_tokens on your completion. An uncapped response on a complex question can generate 4000+ tokens when you needed 200. Set it based on expected output length.
Model Routing — The Highest-Leverage Optimization

Not every task needs the smartest model. Routing requests to appropriate models by complexity is typically the single largest cost lever — 50–70% savings without degrading quality for the tasks that don't need it.

Semantic Caching — Free Tokens

Many user questions are semantically near-identical even if worded differently. A semantic cache works like this:

  1. Embed the incoming query → get vector
  2. Search cache by cosine similarity

Cache invalidation: Semantic caches need TTLs, especially for dynamic data. "What is the status of INC-4521?" cached 2 hours ago is stale. Libraries: GPTCache (Python), or implement yourself with Redis + your vector store. In Spring AI, you can implement this as a pre-processing Advisor that checks Redis before the LLM call is made.

Prompt Caching (Provider-Level)

Both Anthropic (Claude) and OpenAI now offer prompt caching: if the beginning of your prompt (specifically, the system prompt + few-shot examples) is identical across multiple requests, the provider caches the KV-cache for those tokens. You get 50–90% discount on those cached input tokens. This is automatic — you just structure your prompts so the static parts come first and the dynamic parts (user query, retrieved chunks) come last.

    KStream<String, LogEvent> allLogs = builder.stream("raw-logs");

    // Branch 1: known error patterns → direct playbook, no AI needed
    KStream<String, LogEvent>[] branches = allLogs.branch(

        (key, log) -> true                    // everything else → AI
    );

    branches[1].to("ai-triage-queue"); // sent to LLM consumer

    return branches[1];
}

@Repository
public class VectorRepository {

    private final JdbcTemplate jdbc;
    private final EmbeddingModel embeddingModel;

    // Similarity search with metadata filter — raw SQL for full control
    public List<ChunkResult> searchByTenant(String query, String tenantId, int topK) {
        float[] queryEmbedding = embeddingModel.embed(query);
        String pgVector = Arrays.toString(queryEmbedding)
            .replace("[", "[").replace("]", "]"); // format as pgvector literal

        return jdbc.query("""
            SELECT content, metadata,
                   1 - (embedding <=> ?::vector) AS similarity
            FROM vector_store
            WHERE metadata->>'tenant_id' = ?
              AND 1 - (embedding <=> ?::vector) > 0.70
            ORDER BY embedding <=> ?::vector
            LIMIT ?
            """,
            (rs, row) -> new ChunkResult(
                rs.getString("content"),
                rs.getString("metadata"),
                rs.getDouble("similarity")
            ),
            pgVector, tenantId, pgVector, pgVector, topK
        );
    }
}

Batch Ingestion for Large Document Sets
@Service
public class BatchIngestionService {

    private final VectorStore vectorStore;
    private final TokenTextSplitter splitter = new TokenTextSplitter(512, 50, 5, 10000, true);

    // Process 10,000 documents efficiently
    public void ingestBatch(List<Path> documentPaths) {
        // Process in batches of 100 to avoid OOM and rate-limit embedding API
        Flux.fromIterable(documentPaths)
            .buffer(100)                          // batch of 100 files
            .flatMap(batch -> Mono.fromCallable(() -> processBatch(batch))
                .subscribeOn(Schedulers.boundedElastic())
            )
            .doOnNext(count -> log.info("Ingested batch of {} chunks", count))
            .blockLast();
    }

    private int processBatch(List<Path> paths) {
        List<Document> chunks = paths.stream()
            .flatMap(path -> {
                String text = Files.readString(path);
                String docId = path.getFileName().toString();
                var doc = new Document(text, Map.of(
                    "doc_id", docId,
                    "source", path.toString(),
                    "ingested_at", Instant.now().toString()
                ));
                return splitter.apply(List.of(doc)).stream();
            })
            .toList();

        vectorStore.add(chunks);     // Spring AI embeds + stores in one call
        return chunks.size();
    }
}

@Configuration
public class LlmResilienceConfig {

    @Bean
    public RetryRegistry retryRegistry() {
        RetryConfig config = RetryConfig.custom()
            .maxAttempts(3)
            .waitDuration(Duration.ofSeconds(2))
            // Exponential backoff: 2s → 4s → 8s
            .intervalFunction(IntervalFunction.ofExponentialBackoff(2000, 2))
            // Only retry on rate limit (429) and server errors (5xx)
            .retryOnException(e -> e instanceof OpenAiApiException api
                && (api.statusCode() == 429 || api.statusCode() >= 500))
            // Don't retry on bad requests — they'll keep failing
            .ignoreExceptions(BadRequestException.class)
            .build();
        return RetryRegistry.of(config);
    }

    @Bean
    public CircuitBreakerRegistry circuitBreakerRegistry() {
        CircuitBreakerConfig config = CircuitBreakerConfig.custom()
            .failureRateThreshold(50)           // open if 50% of calls fail
            .waitDurationInOpenState(Duration.ofSeconds(30))
            .slidingWindowSize(10)
            .build();
        return CircuitBreakerRegistry.of(config);
    }
}

@Service
public class ValidatedChatService {

    private final ChatClient chatClient;

    public IncidentAnalysis analyzeWithRetry(String log) {
        int attempts = 0;
        while (attempts < 3) {
            try {
                IncidentAnalysis result = chatClient.prompt()
                    .user(buildPrompt(log, attempts))  // stricter prompt on retry
                    .call()
                    .entity(IncidentAnalysis.class);   // throws if JSON invalid

                // Semantic validation — don't trust the model blindly
                if (result.severity() == null || result.rootCause() == null) {
                    throw new IncompleteOutputException("Missing required fields");
                }
                return result;

            } catch (Exception e) {
                attempts++;
                log.warn("LLM output validation failed (attempt {}): {}", attempts, e.getMessage());
                if (attempts == 3) throw new LlmAnalysisException("Failed after 3 attempts", e);
            }
        }
        throw new LlmAnalysisException("Unreachable");
    }

    private String buildPrompt(String log, int attempt) {
        String strictness = attempt == 0 ? "" :
            attempt == 1 ? "\nIMPORTANT: You MUST return valid JSON only. No prose." :
            "\nCRITICAL: Return ONLY this JSON structure, nothing else: {\"severity\":\"P1\",\"rootCause\":\"...\",\"suggestedFix\":\"...\"}";
        return "Analyze this log:\n" + log + strictness;
    }

19. System Design — Scale an AI App to 10,000 Concurrent Users SYSTEM DESIGN
The Bottlenecks at Scale (Identify These First)
  1. LLM API rate limits: OpenAI allows ~10,000 RPM on tier 4. At 10K users each making 1 request/minute, you're at the limit immediately. Solution: async queue + model routing + semantic cache.
  2. LLM latency: Each call takes 1–10s. Synchronous HTTP at scale = thousands of threads blocked. Solution: WebFlux reactive stack (non-blocking I/O) + streaming to keep connections alive.
  3. Vector DB query latency: HNSW search at 10K QPS needs proper indexing and connection pooling. Solution: pgvector with tuned HNSW parameters, HikariCP pool sizing, read replicas.
  4. Embedding API calls: Every unique query needs an embedding before vector search. Solution: semantic cache (skip embedding if cache hit), batch embedding for ingestion.
  5. Token costs: 10K users × 2K tokens/request = 20M tokens/day = significant spend. Solution: model routing, semantic cache, prompt compression.

Situation: "In a personal project, I wanted to solve a problem I noticed at work — when engineers search for past incident solutions, they do keyword searches on Confluence that often miss relevant content because the keywords don't exactly match. I decided to build a semantic search system that understands the meaning of queries, not just keywords."
Task: "I set out to build a RAG pipeline that could answer questions about technical documentation by retrieving the most semantically relevant sections and generating a grounded answer using an LLM — not hallucinating from training data."
Action: "I used LangChain for orchestration, OpenAI's text-embedding-3-small for embeddings, and MongoDB Atlas Vector Search as the vector store. The pipeline had three stages: first, I chunked documents using recursive character splitting at 512 tokens with 50-token overlap to preserve semantic boundaries. Second, I embedded each chunk and stored it in MongoDB. Third, at query time, I embedded the question, retrieved the top-5 chunks by cosine similarity, and injected them into a GPT-4o prompt with a grounding instruction — 'answer only from the provided context.' I also added a similarity threshold of 0.7 to avoid retrieving irrelevant content."
Result: "The system significantly outperformed keyword search for technical queries — questions like 'how do I fix connection pool exhaustion in CF?' returned the exact runbook section, not just documents containing those words. I learned the critical importance of chunking strategy — my first attempt with 2000-token chunks gave poor retrieval because the retrieved chunk was too broad. Smaller chunks at 512 tokens with overlap gave much better precision. This directly maps to what I'd build here on BTP using Spring AI and pgvector."
