1. What is RAG and why is it better than fine-tuning? HIGH LIKELY
Mental Model: Think of RAG like an open-book exam — the model gets to look up answers in real documents before responding. Fine-tuning is like cramming facts into the model's "brain" permanently. Open-book (RAG) is better when facts change; cramming (fine-tuning) is better when you want to change how it writes or behaves.
Interview Answer (say this):
RAG — Retrieval-Augmented Generation — means at query time you fetch the most relevant documents from a knowledge base and inject them into the prompt as context. The model answers using that retrieved content, not just its training data. It's better than fine-tuning for factual knowledge because the knowledge base stays up-to-date without retraining. I built a RAG pipeline using LangChain, MongoDB Atlas Vector Search, and OpenAI embeddings — the user question gets embedded, we do a cosine similarity search, retrieve the top chunks, and pass them to the LLM.
Also worth mentioning: Fine-tuning is still useful — not for injecting facts, but for teaching the model a specific output format or tone. In practice, teams use both: RAG for dynamic knowledge, fine-tuning for consistent behavior. Also, RAG failures are debuggable — you can inspect exactly what chunks were retrieved; fine-tuning failures are a black box.
RAG vector search cosine similarity fine-tuning knowledge base context injection
2. What is an AI agent? What is the ReAct pattern? HIGH LIKELY
Mental Model: A normal LLM answers one question and stops. An agent is an LLM in a loop — it can decide "I need more information", call a tool (search, run code, query a DB), see the result, and keep going until it's done. ReAct = the LLM alternates between Reasoning (what should I do?) and Acting (call a tool), like a person thinking out loud before each step.
Interview Answer (say this):
An AI agent is an LLM that can decide what action to take next and loop until a goal is reached. Instead of one-shot generation, it has access to tools — functions it can call — and it keeps reasoning and acting until it has the answer. The ReAct pattern is how agents reason: the model outputs a "Thought" about what to do, then an "Action" like calling a search tool, then an "Observation" from that tool's result, and it loops. This is how LangChain's AgentExecutor works internally.
Also worth mentioning: The key risk in agents is infinite loops or runaway tool calls. In production you always set a max_iterations limit and a timeout. You also need to think about which tools you give the agent — fewer, well-described tools outperform many vague ones, because the LLM picks tools based purely on their descriptions.
ReAct Thought → Action → Observation tool calling AgentExecutor max_iterations
3. What is LangChain? What is LangGraph? What's the difference? HIGH LIKELY
Mental Model: LangChain is a toolbox for building LLM pipelines — chains, agents, retrievers, all wired together. LangGraph is what you use when your workflow isn't a straight line — it models the agent as a graph with nodes (steps) and edges (transitions), so you can have loops, branches, and human review checkpoints. LangChain = pipeline. LangGraph = flowchart.
Interview Answer (say this):
LangChain is a framework that gives you building blocks for LLM apps — prompt templates, chains, agents, retrievers, memory. LangGraph is built on top of LangChain and adds graph-based control flow: you define nodes (each is a processing step) and edges (transitions between steps, including conditional branches). The key difference is that LangChain's agents are essentially a while-loop, which is hard to control for complex workflows. LangGraph lets you model any flow explicitly — including cycles, parallel branches, and human-in-the-loop pauses — which is why production agent systems use it.
Also worth mentioning: LangGraph supports "checkpoints" — it can save state at any node and resume from there. This is critical for long-running agents that might time out or need human approval mid-flow. Think of it like a state machine where the LLM drives the transitions.

4. What is prompt engineering? What is function calling? CORE
Mental Model: Prompt engineering = writing precise instructions so the LLM behaves predictably, like writing a really good job description for a contractor. Function calling = giving the LLM a menu of tools it can invoke (with input/output schemas), and it tells you which tool to call and with what arguments — your code actually runs it.
Interview Answer (say this):
Prompt engineering is crafting the input to an LLM to get reliable, structured output. The key techniques are: system prompts to set constraints and output format, few-shot examples to show the model what you want, and chain-of-thought to make the model reason step-by-step before answering. Function calling is a separate concept — you define tools as JSON schemas (name, description, parameters), and the LLM returns a structured tool_call object when it wants to use one. Your application then executes the actual function and feeds the result back. This is how agents interact with real systems like databases or APIs.
Also worth mentioning: In Spring AI you implement function calling with @Tool-annotated methods. The model picks the right tool based purely on the description you write, so a good description is as important as the implementation. Also, for structured JSON output, Spring AI's BeanOutputConverter auto-generates a schema from your Java class and injects it into the prompt — zero manual parsing.

5. What is a vector embedding? How does retrieval work? HIGH LIKELY
Mental Model: An embedding is a list of ~1500 numbers that captures the meaning of a piece of text. Similar texts get similar numbers. Retrieval = convert your query to the same kind of number list, then find stored documents whose numbers are closest — that's cosine similarity search. The closer the angle between two vectors, the more semantically similar the texts.
Interview Answer (say this):
A vector embedding is a high-dimensional numerical representation of text produced by an embedding model like OpenAI's text-embedding-3-small. Semantically similar texts have embeddings that are close together in vector space, measured by cosine similarity. In a RAG pipeline: at ingest time you embed each document chunk and store it in a vector database. At query time you embed the user's question, run a nearest-neighbor search in the DB to find the most similar chunks, and inject those chunks into the LLM prompt as context. I used this exact flow with MongoDB Atlas Vector Search in my personal project.
Also worth mentioning: Pure vector search can miss exact keyword matches. The production approach is hybrid search — combine semantic vector search with BM25 keyword search and merge results using Reciprocal Rank Fusion (RRF). Most production RAG systems also add a reranking step — take the top-20 vector results, run a cross-encoder reranker on them, and pass only the top-5 to the LLM. This dramatically improves answer quality.

6. What is Spring AI? CORE
Mental Model: Spring AI is to LLMs what Spring Data is to databases — a portable abstraction layer. You write code against the Spring AI API, and you can swap from OpenAI to Azure OpenAI to Claude by changing one config property. It also has built-in RAG support so you don't have to wire everything manually.
Interview Answer (say this):
Spring AI is the official Spring framework for integrating LLMs into Java applications. Its main value is portability — you write against a common ChatClient interface and switch between OpenAI, Azure OpenAI, Claude, or Ollama via config. The three core abstractions are: ChatClient for chat interactions with support for streaming via Flux, EmbeddingModel for generating vectors, and VectorStore for storing and retrieving embeddings. There's also a QuestionAnswerAdvisor that wires RAG automatically — attach it to your ChatClient and it retrieves relevant documents on every call with zero boilerplate.
Also worth mentioning: Spring AI has an "advisors" chain concept — middleware that wraps every LLM call. You can add a RAG advisor, a logging advisor, a safety-check advisor, and they all run in sequence. It's the same pattern as Spring's HandlerInterceptor chain, which makes it very intuitive if you know Spring MVC.

7. How do you handle hallucinations in production? HIGH LIKELY
Mental Model: Hallucination = the model invents plausible-sounding but wrong facts. You can't eliminate it, but you can contain it with three defenses: ground the model in real documents (RAG), constrain what it's allowed to say (system prompt + output validation), and catch bad outputs before they reach users (guardrails layer).
Interview Answer (say this):
I tackle hallucinations at multiple layers. First, RAG grounding — the system prompt explicitly says "answer only from the provided context; if the answer isn't there, say I don't know." This eliminates most factual hallucinations. Second, temperature zero for factual tasks — lower temperature means the model is less "creative." Third, structural validation — if I expect JSON output, I parse it and retry with a stricter prompt if it fails. And fourth, a guardrails advisor that checks the output for obvious issues like PII leakage or off-topic content before returning to the user. In Spring AI I implement this as a post-processing advisor in the chain.
Also worth mentioning: For critical use cases I use self-consistency — generate 3 responses independently, compare them, and flag cases where they disagree as low-confidence. Also, for entity names specifically (like service names or API endpoints) I cross-validate the model's output against a known registry. A model claiming a service name exists can be checked in milliseconds with a simple lookup.
RAG grounding temperature=0 structural validation retry with stricter prompt guardrails advisor self-consistency
8. What is token optimization / cost management for LLMs? CORE
Mental Model: LLMs charge per token (roughly 0.75 words). Your bill = (prompt tokens + completion tokens) × price per model. Cost optimization = send fewer tokens and use cheaper models where possible. It's the same as query optimization in databases — don't fetch what you don't need.
Interview Answer (say this):
Three main levers. First, model routing — use a cheap, fast model like GPT-4o mini or Claude Haiku for simple tasks like classification or extraction; only escalate to GPT-4o or Opus for complex reasoning. This alone can cut costs by 60-70%. Second, prompt compression — summarize old chat history instead of passing the full transcript, and remove unnecessary filler from system prompts. Third, semantic caching — embed the user query and cache the response; if a near-identical question comes in with cosine similarity above 0.97, return the cached answer instead of calling the API. I also always set a max_tokens cap on completions to avoid surprise costs.
Also worth mentioning: For token counting in Java, use the jtokkit library — it's a port of OpenAI's tiktoken. Count tokens before the API call so you can proactively truncate or summarize context rather than getting a 400 error for exceeding the context window. Also, in RAG pipelines, retrieved chunk size directly impacts prompt token count — tuning chunk size is both a retrieval quality and a cost decision.

9. How would you build an AI agent that auto-triages cloud incidents from logs? DESIGN
Mental Model: Think of it as three layers: Kafka streams the logs in real-time → a rules engine handles known errors instantly (no AI needed) → an AI agent handles unknown errors by looking up similar past incidents and generating a triage report. The agent decides severity, suggests a fix, and routes the alert to the right team.
Interview Answer (say this):
I'd design it as a four-layer pipeline. Layer one: stream cloud application logs into Kafka topics, one per service. A Kafka Streams job filters out DEBUG/INFO and forwards only WARN/ERROR events. Layer two: a Spring Boot consumer applies a fast rules engine for known error patterns — OOM errors, DB connection failures — these get immediate playbook-based triage. Unknown errors escalate to the AI agent. Layer three: a LangGraph agent with four nodes — classify the error severity (P1/P2/P3), do RAG retrieval over past incident runbooks, generate a structured triage report with root cause and suggested fix, then a human-review gate that routes P1 to PagerDuty immediately and P2/P3 to a ticket queue. Layer four: a feedback loop where resolved incidents feed back into the RAG knowledge base.
Also worth mentioning: I'd add an entity validator as a guardrail — before the alert fires, cross-check any service names the LLM mentions against the actual service registry. This prevents hallucinated service names from causing confusion.

10. What is multi-agent orchestration? CORE
Mental Model: One agent trying to do everything is like a single developer handling frontend, backend, QA, and deployment alone — it works for small tasks but doesn't scale. Multi-agent = a team. An orchestrator breaks the task and delegates to specialist agents. Each specialist is focused, faster, and cheaper to run.
Interview Answer (say this):
Multi-agent orchestration is when multiple AI agents collaborate on a task, each responsible for a specific capability. The most common pattern is Orchestrator-Worker: an orchestrator LLM breaks the task into subtasks and delegates them to specialist agents — for example, a Retrieval Agent that searches the knowledge base, a Code Agent that writes or executes code, and a Validation Agent that checks the output. They communicate via message passing, and the orchestrator aggregates their results. Frameworks like AutoGen from Microsoft make this explicit, with agents that can critique each other's outputs in a loop until the result is good enough.
Also worth mentioning: The hardest part of multi-agent systems isn't the agents themselves — it's shared state management and loop termination. You need to define clear stopping conditions otherwise agents can argue indefinitely. Also, parallel agent execution needs careful coordination; LangGraph handles this with its fork/join graph edges, where you can branch out to multiple agents in parallel and merge their results at a join node.
